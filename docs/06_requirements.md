# 6. Требования

Приоритеты: **MoSCoW** (Must / Should / Could). Каждое обязательное требование имеет критерий приёмки, по которому можно проверить выполнение.

## 6.1. Функциональные требования

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| FR-1 | Регистрация и вход по e-mail и паролю | Must | Пользователь регистрируется и входит; неверный пароль отклоняется с понятной ошибкой |
| FR-2 | Роли: студент, преподаватель, администратор | Must | Студент не видит Teacher Mode; запрос к чужим данным возвращает 403 |
| FR-3 | Главный экран с модулями | Must | Отображаются доступные модули и прогресс по каждому |
| FR-4 | Модуль «Личный бюджет» со сценариями | Must | Минимум 3 сценария с ветвлением; решение меняет баланс |
| FR-5 | Модуль «Кредиты и рассрочка» | Must | Расчёт переплаты совпадает с эталонным значением (см. [08_verification_plan.md](08_verification_plan.md)) |
| FR-6 | Минимум один сценарий по распознаванию мошенничества | Must | Студент может выбрать ответ; получает пояснение |
| FR-7 | Образовательная обратная связь после каждого решения | Must | После каждого решения выводится текст «что произошло и почему» |
| FR-8 | Сохранение игровой сессии и продолжение | Must | После перезапуска приложения сессия продолжается с того же шага |
| FR-9 | Расчёт последствий решений на сервере | Must | Клиент отправляет только выбор; итоговые показатели возвращает сервер |
| FR-10 | Прогресс и очки по модулям | Must | Очки начисляются сервером; прогресс отображается в процентах |
| FR-11 | Teacher Mode: статистика группы | Should | Преподаватель видит средние показатели и типичные ошибки группы |
| FR-12 | Классификация ошибок | Should | Каждая ошибка относится к одной из категорий (например, нет резервного фонда) |
| FR-13 | Экспорт отчёта по группе в CSV | Should | Файл открывается и содержит данные по студентам |
| FR-14 | Достижения и рейтинг | Could | Расширение, вводится только после MVP |
| FR-15 | Модули «Сбережения и инфляция», «Налоги и инвестиции» | Could | Расширение, вводится только после MVP |
| FR-16 | Ввод личных финансов: доход, обязательные расходы, накопления, долги | Must | Введённые значения сохраняются в профиле; свободный остаток (доход − расходы) считается на экране; сценарии используют эти значения |
| FR-17 | Персонаж: аватар и имя в игре | Should | Пользователь выбирает один из вариантов аватара и имя; аватар отображается на главном экране и в профиле; значения можно изменить |
| FR-18 | Шесть сценариев с расчётами и ветвлением | Must | Сценарии модулей «Бюджет», «Кредиты», «Мошенничество» и «Накопления» проходятся до итога; расчёты переплаты, срока погашения и реальной доходности совпадают с эталонами в [tests/fixtures/calculations.json](../tests/fixtures/calculations.json) |
| FR-19 | Личный план: цель резерва и прогресс накопления | Should | На главном экране показаны свободный остаток, цель резерва (3 месяца обязательных расходов) и процент накопленного |

## 6.2. Нефункциональные требования

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| NFR-1 | Производительность API | Must | 95% запросов сценариев выполняются не дольше 500 мс при 50 одновременных пользователях на тестовом стенде |
| NFR-2 | Кроссплатформенность клиента | Must | Приложение собирается для Android и iOS из одного кода |
| NFR-3 | Безопасность | Must | Пароли хешируются (bcrypt или аналог); токены не хранятся в открытом виде; SQL-инъекции отсутствуют (параметризованные запросы); HTTPS на стенде |
| NFR-4 | Защита от подмены данных клиентом | Must | Изменение баланса вне сервера невозможно (проверяется тестом) |
| NFR-5 | Надёжность сессии | Should | Сессия восстанавливается после обрыва сети при повторной отправке |
| NFR-6 | Удобство (SUS) | Should | Средний балл SUS в пилоте не ниже 68 |
| NFR-7 | Адаптивный интерфейс | Must | Интерфейс корректно отображается на экранах 360–430 px по ширине |
| NFR-8 | Сопровождаемость | Should | Покрытие юнит-тестами ключевой логики не ниже 70% |
| NFR-9 | Развёртывание | Should | Сервер запускается командой `docker compose up` |

FR-16–FR-19 добавлены 20.10.2026 по итогам прототипа версии 2 ([prototype/index.html](../prototype/index.html)). Прототип — макет интерфейса и демонстрация; он не заменяет требования к клиенту.

## 6.3. Ограничения

- Платформа клиента — мобильное приложение на Flutter (как в утверждённой теме). Веб-версия прототипа показывается только как демонстрация интерфейса, а не как продукт; перенос экранов во Flutter запланирован на дипломный этап.
- Срок: защита апрель 2027 г.; MVP к концу февраля 2027 г.
- Команда: 2 человека; работа ведётся через Pull Request с ревью напарника.
- Финансовые расчёты проверяются по консультации Ж. Тельмана и открытым формулам; в проекте не используются реальные банковские данные.

## 6.4. Связь с MVP

Все требования с приоритетом **Must** образуют обязательный минимум (см. [01_project_proposal.md](01_project_proposal.md), раздел 1.6). Требования **Could** и часть **Should** выполняются только после MVP.
