# 5. Сравнение технологий

Рассматриваются 4 ключевых решения (требование: не менее 3), для каждого 2–3 альтернативы. Выбор обосновывается требованиями из [06_requirements.md](06_requirements.md).

## 5.1. Решение T1. Клиентская платформа

| Вариант | Плюсы | Минусы | Оценка для проекта |
|---|---|---|---|
| **Flutter (Dart)** — выбран | Один код для Android и iOS; готовые виджеты; адаптивный интерфейс; опыт команды (стажировка) | Размер приложения больше нативного | Соответствует NFR-2 (два мобильных стора по одному коду) |
| React Native (JavaScript) | Один код, большое сообщество | Зависимость от мостов; у команды меньше опыта | Альтернатива |
| Нативная разработка (Kotlin / Swift) | Максимальная производительность | Два отдельных проекта, больше работы | Не подходит по срокам |

## 5.2. Решение T2. Серверная платформа

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **Node.js + Express** — выбран | Единый язык с инструментами тестирования; быстрый REST API; опыт команды (проект Crown на Express) | Менее строгая типизация без TypeScript | Соответствует требованиям REST и тестирования (Jest, Supertest) |
| Spring Boot (Java) | Строгая архитектура, зрелая экосистема | Больше шаблонного кода, крутая кривая для команды | Альтернатива |
| Django (Python) | Встроенная админка, ORM | Меньше опыта команды в REST с мобильным клиентом | Альтернатива |

## 5.3. Решение T3. СУБД

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **PostgreSQL** — выбран | Транзакции, ограничения целостности, сложные аналитические запросы | Больше настройки, чем у NoSQL | Соответствует требованию целостности и отчётам |
| MongoDB | Гибкая схема для сценариев | Слабее при аналитике и согласованности расчётов | Альтернатива; отвергнута по требованию целостности |
| MySQL / MariaDB | Простота, зрелость | Меньше возможностей для JSON и аналитики | Альтернатива |

## 5.4. Решение T4. Аутентификация и доступ

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **JWT с обновлением токена + RBAC** — выбран | Подходит для мобильного клиента; роли трёх типов | Нужно грамотно хранить refresh-токен | Соответствует NFR-3 (безопасность) |
| Серверные сессии (cookie) | Простой отзыв сессии | Хуже подходит для мобильного клиента | Альтернатива |
| OAuth 2.0 / внешний провайдер | Не нужно хранить пароли | Зависимость от внешнего сервиса; избыточно для MVP | Альтернатива |

## 5.5. Вывод

Выбранный стек (Flutter, Node.js/Express, PostgreSQL, JWT, Docker) обоснован требованиями мобильного клиента, целостностью расчётов, аналитикой по группам и опытом команды. Окончательные версии библиотек фиксируются в `src/` при создании каркаса.
